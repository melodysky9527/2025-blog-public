让 AI 帮忙改代码时，除了看它能否完成任务，还应知道它能读哪些文件、改哪些目录、连接哪些网络地址。

OpenAI 在 2026 年 11 月 18 日的工程文章《Inside the Codex sandbox》中，解释了 Codex 怎样在用户已有环境里运行命令，同时施加文件系统和网络限制。[1] 这篇说明提供了一个实用视角：把任务要求与进程实际拥有的访问范围一起考虑。

## 写入、读取、联网要分别看

官方文章以 Git 仓库作为工作区根目录，说明内置 `:workspace` 权限配置的取舍：[1]

| 范围 | 文章描述的行为 | 使用时应理解的含义 |
| --- | --- | --- |
| 写入 | 允许在工作区内写入，但 `.git`、`.codex` 等目录保持只读 | 能修改源代码，不代表工作区内所有位置都能随意修改 |
| 读取 | 在操作系统原有权限允许的范围内，允许较广的文件读取 | 工作区之外的配置、库和部分敏感文件也可能可读 |
| 网络 | 禁用网络访问 | 下载依赖和访问外部服务可能需要额外权限 |

这里描述的是文章中的特定权限配置，不代表所有客户端、版本和组织设置都采用相同选项。实际使用时，要查看当前会话生效的配置。

尤其容易误解的是读取范围：某个目录不能写入，并不意味着其中的内容不能被读取。官方解释，编译器、运行时与构建工具经常依赖仓库以外的文件，因此广泛读取有实用价值，也带来了敏感配置可能被读到的取舍。[1]

## 根据任务确定访问范围

下面三种情况，可以作为设置权限时的思考起点；它们是本文建议，具体设置方式以当前工具为准。

**只读代码审阅**：先让助手读取相关代码与任务说明，输出问题位置和依据。需要查资料时，再单独考虑网络访问。审阅任务并不必然需要写入权限。

**修复一个局部错误**：明确允许修改的项目范围，提供复现方式和验收标准。完成后检查实际改动，并查看测试结果及未完成项。

**构建时需要下载依赖**：确认需要下载什么、从哪里获取、会运行哪些安装步骤，再补充必要权限。把一次下载需求解释成长期扩大所有访问范围，通常缺少足够依据。

这个过程的重点，是让“完成任务需要什么”具体可见。权限不足时，应说明受阻的操作；调整权限时，也应清楚新增了哪种能力。

## 沙箱仍然有需要留意的边界

官方文章特别举了一个例子：工作区里安装的工具可能位于 `node_modules` 等通常被 Git 忽略的目录。若这些工具被修改，变更未必出现在常规的 `git status` 结果中；当编辑器在沙箱之外调用它们时，可能执行修改后的代码。[1]

因此，“Git 没显示异常”不能覆盖所有工作区风险。对会在后续自动运行的脚本、依赖工具和编辑器任务，也应结合实际情况检查。

文章将沙箱纳入多层防护：一层限制命令能够访问的文件和网络，其他层帮助模型按用户意图使用这些权限。[1] 对使用者而言，可以据此形成一个习惯：既审查结果，也留意执行环境中发生了什么。

## 在点击授权前，先把动作说清楚

遇到扩大权限的请求，可以用四项信息判断是否与任务相符：

1. 要执行的具体命令或操作是什么。
2. 会读取、写入哪些位置，或连接哪些服务。
3. 这一步为什么是当前任务所必需的。
4. 完成后如何验证结果，失败时会留下什么状态。

这些信息也能帮助你发现不必要的操作。比如，本来只是本地整理代码，却要求访问与任务无关的服务，就应先追问其必要性。

使用 AI 编程助手时，清楚的任务、合适的权限和可以复核的结果需要配套。让助手明确报告运行过的检查、未解决的问题以及权限阻碍，比只接收一句“已经完成”更便于继续工作。
