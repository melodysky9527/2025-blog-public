如果你经常给 AI 重复交代同一套工作步骤，可以试着把它写成一个 Skill：保存为文件，随项目维护，让下一次任务有明确的起点。

GitHub 在 2026 年 11 月 12 日发布的 Agent Skills 实用指南，讨论的正是这件事。它把 Skill 描述为以 `SKILL.md` 为核心、可进行版本管理的目录，用来说明某项重复任务应该在什么时候执行、怎样完成。[1] 对个人和小团队而言，最有价值的起点，往往就是那项你已经解释过很多次的工作。

## Skill 里应该写清哪些内容

从 GitHub 的指南中，可以整理出几个实用问题：这项任务何时适用，需要什么输入，最后要交付什么，以及怎样判断完成。

假设你的团队反复要求 AI 检查发布说明，那么“帮我认真检查”就不够具体。更有用的说明应指出：读取哪份变更记录，核对哪些版本号与链接，如何处理无法确认的内容，以及把发现的问题放在哪里。

下面是本文自拟的内容示例，用来展示这种写法。它尚未经过客户端适配与运行验证：

```markdown
任务：检查发布说明

输入：本次变更记录、版本号、发布说明草稿。

步骤：
1. 核对每个新增功能能否对应到变更记录。
2. 检查版本号、日期和文档链接是否一致。
3. 将无法确认的描述列为问题，不补造细节。

输出：按严重程度排序的问题清单，并附文件位置。

边界：不修改版本号，不上传文件，不执行发布。
```

这样的说明把重复要求留在文件里，也让协作者能够审阅和修改。真正落地时，还需要按使用的客户端要求补齐目录、元信息与工具配置。

## 工作步骤与项目配置分别维护

GitHub 的 Data Forge 示例把项目名称、平台和业务细节放进 manifest，也就是一份供多个步骤共同读取的配置文件。相关 Skills 共享这些信息，减少各自猜测项目背景的机会。[1]

这对普通项目也有启发：把“检查发布说明的方法”写在 Skill 里，把“这个项目的版本文件在哪里、文档域名是什么”放在项目配置中。项目搬家或更换平台时，优先更新配置，再检查哪些步骤需要适配。

还要注意，仓库里原本存在的写法未必就是团队标准。GitHub 指南也提醒，应把发现的项目细节与团队要求分开，让涉及业务判断的内容可以被人复核。[1]

## 跨客户端复用，需要检查运行环境

GitHub 文章标题用了“Build once, run on any agent”，但正文明确说明：工具、凭据、模型和权限会随承载客户端而变化。Skill 可以描述如何查询数据库，却不会因此获得数据库访问权限；配置中选择了某个引擎，也不会自动把对应的命令行工具安装好。[1]

它的示例还采用打包脚本，为不同客户端生成各自的配置文件。因此，迁移时可以沿用工作知识，仍要逐项检查：

- 客户端能否在合适的任务中识别并加载这个 Skill。
- 引用的文件、脚本和工具是否存在。
- 执行所需的访问范围与凭据是否已经配置。
- 输出是否包含要求的证据，失败时能否说清原因。

拿同一组输入在两个环境里分别验证，才能知道你的流程实际能复用到什么程度。

## 验收标准也要一起保存

只有操作步骤，流程仍可能停在“AI 说它做完了”。我更建议把验收方式一并写进去：检查结果需要附原文位置，代码变更需要说明运行过哪些测试，无法完成的步骤需要列出阻碍。

GitHub 的 Proof Agent 示例使用独立核查者审阅变更，并要求结论附证据。文章同时说明，示例中的静态审阅不会执行代码或测试；如果某项检查必须阻止合并或部署，仍需在仓库规则与 CI 中配置实际门槛。[1]

这也说明了 Skill 的适用范围：它很适合保存有边界、可重复的工作方法。若你需要稳定接口、长期状态或由模型之外的系统强制执行权限，GitHub 建议考虑应用程序。[1]

从一项小工作开始最容易看出价值。把它的输入、步骤、输出和停止条件写清，提交到版本管理，再根据真实执行结果改进。维护一份能持续使用的工作说明，比收集一大批没有验证过的 Skills 更有帮助。
